## Introduction

Chapter 35 made the editor's correctness **verifiable** through testing. But tests describe the conditions we anticipated; real programs fail in ways we did not. When the editor misbehaves—a cursor appears on the wrong line, a keystroke runs the wrong command, text corrupts after a save—the question is no longer whether the design is correct, but where it first became incorrect.

Debugging a terminal editor is hard for structural reasons. It is stateful, event-driven, split across architectural boundaries, and it talks to a terminal it does not control. A defect can originate far from its symptom, so the goal is to make behavior observable and trace each operation until it first diverges from expectation.

This chapter treats debugging as a disciplined engineering skill rather than improvisation. We build the model progressively:

```text
Motivation — why editors are difficult to debug
    ↓
Safety nets — assertions, debug builds, debuggers, breakpoints
    ↓
Visibility — inspecting state, input, and rendering
    ↓
Evidence — logging, tracing, memory diagnostics
    ↓
Reproduction — and the mistakes that undermine it
```

We begin by explaining why the editor's architecture makes bugs hard to locate, then build a set of tools: assertions that state invariants, debug builds that preserve them, and a debugger used to find the first incorrect state. We examine breakpoints, state inspection, and targeted debugging of the input and rendering pipelines. We then add logging and tracing for behavior that cannot be paused, and diagnose memory errors through ownership. We close by learning to reproduce bugs reliably and by reviewing the mistakes that turn debugging into guesswork.

## Learning Objectives

By the end of this chapter, you should be able to:

- Explain why an editor's statefulness, pipeline, and terminal interaction make bugs hard to locate.
- Define the "first incorrect state" and use it to guide a debugging investigation.
- Explain what assertions check and why they express invariants rather than error handling.
- Describe how debug builds make state observable without changing program behavior.
- Use a debugger to step, inspect variables, and read the call stack.
- Place breakpoints that answer specific questions about execution.
- Inspect editor state—cursor, document, viewport, buffer, and dirty—at module boundaries.
- Debug input by tracing the transformation from raw bytes to commands.
- Debug rendering by separating incorrect state from an incorrect presentation.
- Use logging and tracing to observe behavior that cannot be paused.
- Diagnose memory errors through bounds, lifetime, and ownership reasoning.
- Reproduce a bug from the smallest deterministic sequence of operations.
- Recognize and avoid common debugging mistakes.
