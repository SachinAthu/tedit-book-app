This chapter studied the simplest data structure that can represent editable text: the **array**. A line maps naturally onto a sequence of characters, and the editor stores its Document as a vector of independently stored lines, each of which holds its own contiguous character sequence.

We saw where arrays get their power. Their elements occupy a **contiguous region of memory**, so the address of an indexed element follows directly from the base address, the index, and the element size. The character at the cursor can therefore be found immediately rather than by stepping through every preceding element. This is why the cursor's row-and-column model fits an array-based representation so naturally.

That same contiguity produces the central trade-off of the chapter:

> **Arrays provide simple and efficient indexed access, but inserting or deleting elements in the middle can require moving other elements.**

We made this concrete by distinguishing **length** (the elements that belong to the sequence) from **capacity** (the amount of storage available). A **fixed-size array** has a capacity set at creation and cannot grow, which makes it unsuitable for document text but still useful for data with a known bound, such as screen dimensions.

A **dynamic array** keeps the contiguous representation and adds `data`, `length`, and `capacity`. When its capacity is exhausted, it grows by allocating larger storage, copying the existing elements, and releasing the old allocation—an operation that may move the entire sequence to a new address. Growing by a substantial factor keeps resizes rare, so the amortized cost of appending stays low, applying the complexity ideas from Chapter 24.

We then traced the two operations that dominate editing. **Insertion** shifts elements to the right, moving from the end toward the insertion point so no element is overwritten before it has been moved, and only then places the new character. **Deletion** shifts the following elements to the left to close the gap and decreases the length, without necessarily shrinking the capacity. Both costs depend on position: editing near the beginning of a long line can require moving almost the entire sequence.

Applied to text, a **C string** is a contiguous sequence of bytes terminated by a null byte; finding its end means scanning rather than consulting a stored length. The editor's Document deliberately does not use C strings: per **ADR-021: Text Encoding Strategy**, it stores decoded Unicode code points, line by line, with UTF-8 handled only at the file boundary. A **dynamic string** captures the growable pattern with three fields—`data`, `length`, and `capacity`—separating the logical size of the text from the physical memory allocated to store it.

Finally, we placed this representation in context. A dynamic array is not the only way to store editable text. We compared fixed arrays, dynamic arrays, linked lists, Gap Buffers, Piece Tables, and Ropes, each balancing simplicity, indexed access, modification cost, memory usage, and complexity. There is no universally best representation; the appropriate choice depends on the workload.

For our editor, the deliberate choice remains the one recorded as **ADR-013: Document Representation**:

```text
Document
   │
   ▼
Vector of lines
   │
   ▼
Contiguous character storage
```

A vector of lines maps directly onto the cursor's row-and-column model, line-by-line rendering, line splitting, and line merging, and it is simple enough to understand and debug while the rest of the editor is built. The more sophisticated structures this chapter surveyed exist because professional editors face workloads—enormous documents, cursor-local editing, frequent middle edits—that make the movement cost of a contiguous sequence significant. Understanding this baseline is what makes those structures meaningful.

The most important takeaway:

> **The representation of text determines which operations are cheap and which become expensive. Arrays give us a simple, direct baseline whose only real weakness—moving elements for middle edits—is exactly the problem the specialized text buffers we study next were designed to address.**

## Common Mistakes

### Confusing length with capacity

Length counts the elements that currently belong to the sequence; capacity counts the elements the allocated storage can hold. Treating them as interchangeable leads to writing into positions the allocation does not own, or believing a line is longer than its stored text.

### Writing beyond capacity

Placing an element at index `length` when `length == capacity` writes outside the allocated region. The editor must check capacity before every insertion and resize when it is exhausted, not after.

### Shifting in the wrong direction during insertion

Insertion must shift elements from the end toward the insertion point. Shifting from the insertion point toward the end overwrites the very data that still needs to move, destroying part of the sequence before it is relocated.

### Forgetting to update length

Insertion, deletion, and resizing all change the logical size of the sequence. Leaving `length` stale means the editor either reads elements that are no longer part of the text or silently drops elements it thinks were removed.

### Keeping pointers into storage after reallocation

A resize can move the entire allocation to a new address. Any pointer saved into the old storage no longer refers to the current text, so code that retains such pointers after a grow must be rederived from the new `data`.

### Treating C strings and the editor's code-point representation as identical

A C string is a null-terminated byte sequence; the Document stores decoded Unicode code points. Assuming they are the same conflates bytes with characters and would break cursor positions and editing semantics for non-ASCII text.

### Assuming deletion must immediately shrink capacity

Deleting elements reduces `length` but rarely needs to shrink the allocation. Shrinking eagerly causes repeated allocate-and-copy cycles as the user types and deletes. The available capacity is exactly what makes a later insertion cheap.

### Growing by one element at a time

Increasing capacity by exactly one on every resize turns each append into an allocate-and-copy of the entire sequence. A growth policy that multiplies the capacity (such as doubling) makes resizes rare and keeps the amortized cost low.
