title: '24.4 Big-O Notation'
description: "Introduces Big-O notation, common complexity classes, and why growth rate matters more than constant factors."
---

Once we know what input size we are measuring, we need a way to describe how an operation's cost grows as that input becomes larger.

The most common notation for this purpose is **Big-O notation**.

Big-O gives us a language for describing the growth of an algorithm's resource requirements.

It allows us to say:

> "As the input becomes larger, this operation grows at approximately this rate."

It does not tell us the exact execution time.

## Why We Do Not Measure Seconds

Suppose two computers run the same operation.

```text
Computer A
    → 1 millisecond

Computer B
    → 0.2 milliseconds
```

The measured times are different even though the algorithm is identical.

Execution time depends on many factors:

- processor speed
- memory performance
- compiler optimizations
- operating system behavior
- implementation details
- current system load

A measurement taken on one machine therefore does not tell us how the algorithm scales on another machine.

Instead, we want to understand how the amount of work changes when the input changes.

Consider an operation that examines every element in a collection.

```text
10 elements
    → approximately 10 elements examined

1,000 elements
    → approximately 1,000 elements examined

1,000,000 elements
    → approximately 1,000,000 elements examined
```

The amount of work grows with the input size.

We can describe this growth as:

```text
O(n)
```

where `n` represents the relevant input size.

## The Meaning of O(n)

Suppose `n` represents the number of characters that an operation may need to examine.

An `O(n)` operation has work that grows proportionally with `n`.

Conceptually:

```text
Input size     Relative work

10             █
100            ██████████
1,000          ██████████████████████████████████████████████████
```

The exact number of processor instructions is not important here.

What matters is the **growth pattern**.

If the input becomes ten times larger, an `O(n)` operation may require roughly ten times as much work.

## Common Complexity Classes

Several complexity classes appear frequently when analyzing algorithms.

### O(1) — Constant Time

An `O(1)` operation performs a bounded amount of work that does not grow with the input size.

For example, accessing an element when its location is already known can be considered constant time:

```text
elements:

A B C D E F G H

          ^
          known position
```

Whether the collection contains ten elements or ten million elements, the operation does not need to examine the entire collection to reach that known position.

Conceptually:

```text
Small input  → same amount of work
Large input  → same amount of work
```

This is why constant-time operations are generally attractive.

### O(log n) — Logarithmic Time

An `O(log n)` operation grows more slowly than the input itself.

The classic pattern is repeatedly reducing the remaining search space.

For example:

```text
1,000,000 items
       │
       ▼
   reduce search
       │
       ▼
   reduce again
       │
       ▼
     ...
```

The amount of work increases slowly as the input grows.

We will not rely heavily on logarithmic algorithms in the baseline text-buffer implementation, but this complexity class becomes useful when discussing more sophisticated data structures later in the volume.

### O(n) — Linear Time

An `O(n)` operation performs work proportional to the input size.

For example, scanning every character in a sequence:

```text
A B C D E F G H
----------------
check each item
```

If there are twice as many elements, there can be approximately twice as much work.

Many straightforward text-processing operations naturally have this behavior.

### O(n log n) — Linearithmic Time

An `O(n log n)` operation grows faster than `O(n)` but much more slowly than `O(n²)`.

This complexity commonly appears in efficient sorting algorithms and other divide-and-conquer algorithms.

It is useful to recognize the class even when we do not implement such an algorithm directly in our editor.

### O(n²) — Quadratic Time

An `O(n²)` operation grows much more rapidly.

A common pattern is comparing many elements with many other elements:

```text
A B C D
│ │ │ │
│ │ │ └── compare
│ │ └──── compare
│ └────── compare
└──────── compare
```

If the input doubles, the amount of work can grow by approximately four times.

This is why quadratic algorithms can become problematic as input sizes increase.

## Comparing Growth

The differences become clearer when we compare several complexity classes:

```text
Better scaling
      │
      ▼
O(1)
O(log n)
O(n)
O(n log n)
O(n²)
      │
      ▼
Worse scaling as n becomes large
```

This ordering is useful as a general rule when comparing algorithms that operate on sufficiently large inputs.

However, it should not be interpreted as:

> "Every `O(n)` algorithm is always faster than every `O(n²)` algorithm."

Big-O describes asymptotic growth. It does not capture every constant factor or implementation detail.

For small inputs, an algorithm with a theoretically worse complexity may sometimes perform better in practice.

## Big-O Ignores Constant Factors

Suppose an operation performs:

```text
5n
```

units of work.

Another performs:

```text
100n
```

units of work.

Both are:

```text
O(n)
```

because both grow linearly with `n`.

Big-O focuses on the growth rate rather than the exact multiplier.

Similarly:

```text
3n + 10
```

is also:

```text
O(n)
```

because as `n` becomes large, the linear term dominates the fixed amount of additional work.

This simplification makes it possible to compare algorithms at a higher level.

## Big-O Does Not Mean "Exactly n"

This is a common misunderstanding.

When we write:

```text
O(n)
```

we are not saying:

> "The algorithm performs exactly `n` operations."

The actual implementation may perform:

```text
2n + 5
```

or:

```text
50n + 100
```

or some other amount of work that grows linearly.

The notation communicates the **growth category**, not an exact instruction count.

## Big-O in the Editor

Now we can apply the notation to the editor.

Suppose an insertion operation needs to move the characters after the cursor.

```text
A B C D E F G H
      ^
   cursor

Insert X

A B C X D E F G H
```

If the number of characters that may need to move is `L`, where `L` is the relevant line length, then the operation may have linear growth:

```text
O(L)
```

The important part is not memorizing `O(L)`.

The important reasoning is:

```text
What does the operation touch?
        ↓
Characters after the cursor
        ↓
How many can there be?
        ↓
Up to L
        ↓
Therefore the work grows with L
```

That reasoning process is what we will use throughout the rest of this volume.

## Complexity Is a Model

Big-O is a model of algorithmic growth.

It deliberately leaves out many details of actual execution.

That is useful because it allows us to reason about designs before implementing them.

For example, before choosing a text-buffer structure, we can ask:

```text
Insert character
       │
       ├── What must move?
       │
       ├── How much data can be affected?
       │
       └── How does that amount grow?
```

We can perform this analysis without knowing the exact processor on which the editor will eventually run.

That makes complexity analysis an architectural tool as much as an algorithmic one.

## A Practical Rule

When analyzing an operation, follow this sequence:

```text
1. Identify the operation
        ↓
2. Define the relevant input size
        ↓
3. Identify the work performed
        ↓
4. Determine how that work grows
        ↓
5. Express the growth using Big-O
```

For example:

```text
Operation:
Insert character

Input size:
Length of affected line, L

Work:
Move characters after insertion point

Growth:
Proportional to L

Complexity:
O(L)
```

This simple method will become increasingly useful as we examine different ways of storing editable text.

Big-O gives us the vocabulary to compare those structures, but it is only one part of the analysis.

## Summary

Big-O notation describes how an operation's resource requirements grow as its input becomes larger, without committing to an exact execution time on a particular machine. It focuses on the growth pattern rather than constant factors, so 5n, 100n, and 3n + 10 are all O(n) because the linear term dominates as n grows. Common classes include O(1) constant time, O(log n) logarithmic time, O(n) linear time, O(n log n) linearithmic time, and O(n²) quadratic time, ordered from better to worse scaling for sufficiently large inputs. Big-O is a model rather than a precise instruction count: an O(n) operation may still perform 2n + 5 or 50n + 100 units of work, and a theoretically worse algorithm can occasionally win on small inputs. In the editor, the method is to identify what an operation touches, how much of it can be affected, and how that amount grows; character insertion that may move up to L characters, for example, is O(L). The notation therefore serves as an architectural tool for comparing text-buffer designs before they are implemented.

We also need to understand best-case and worst-case behavior, because the same operation may have very different costs depending on the circumstances.
