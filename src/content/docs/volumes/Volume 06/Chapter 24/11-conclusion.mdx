This chapter gave us the vocabulary and method to answer the central question of Volume VI:

> **How much work does an editor operation require, and how does that work grow as the document grows?**

Cost is multi-dimensional. We examined **time** (how computational work grows), **space** (how much additional memory an operation requires), **memory locality** (how efficiently data is accessed), and **latency** (the delay the user actually experiences). We saw that every analysis must begin by identifying the operation's relevant input size—affected line length, number of characters or lines, file bytes, or visible screen dimensions—and that no single `n` applies to every operation.

We then developed the tools for describing growth: **Big-O notation** for asymptotic behavior, **best, average, and worst cases** for the range of possible costs, and **amortized complexity** for judging the cost of a sequence of operations rather than a single one.

The most important takeaway:

> **Complexity is a property of an operation together with the data structure that implements it. The representation of text determines which operations are cheap and which become expensive as the document grows.**

That conclusion is what makes the rest of this volume necessary: to compare different text-buffer structures, we must first be able to analyze their costs.

### Thought Experiments

1. A document contains a single line of one million characters stored in a contiguous array. The cursor is near the beginning, and the user inserts a character. Roughly how much work is performed, and what does that imply for latency?
2. An operation uses `O(1)` additional memory, while a second operation copies the entire document. Under what conditions might the second be a reasonable engineering choice despite using more memory?
3. A dynamic array occasionally resizes and copies all its elements. Even though the amortized cost of an insertion is low, why might a user still occasionally experience a delay?

## Common Mistakes

### Using complexity as a label of "fast" or "slow"

Big-O describes growth, not a verdict. An operation with higher complexity can still be the right choice, and a lower-complexity operation is not automatically better once constant factors, memory, and simplicity are considered.

### Treating correctness as sufficient

An operation can produce the correct document while requiring enormous work. Efficiency is a separate question from correctness.

### Using a single "n" for every operation

There is no one universal document size. Character insertion relates to line length, saving relates to encoded file size, and rendering relates to the visible screen area. The input size must be identified per operation.

### Confusing average-case with amortized analysis

Average-case analysis depends on assumptions about the distribution of inputs. Amortized analysis distributes the cost of occasional expensive operations across a sequence without such probability assumptions.

### Ignoring worst case in an interactive application

The user experiences the worst case directly: an expensive operation inside one event-loop iteration becomes visible latency between a key press and the updated screen.

### Confusing best case with best design

A cheap best case is not enough. If the expensive case is the common one, the operation is expensive in practice.

### Believing complexity alone describes real-world performance

Two `O(n)` algorithms can behave very differently because of constant factors, memory access patterns, and allocation behavior. Big-O and locality are complementary, not interchangeable.

### Assuming an operation's complexity is fixed

The same logical operation can have very different costs under different representations. Complexity must be analyzed together with the data structure that implements the operation.
