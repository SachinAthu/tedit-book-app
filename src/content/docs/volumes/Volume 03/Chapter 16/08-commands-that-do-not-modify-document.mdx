---
title: 16.8 Commands That Do Not Modify the Document
description: Explains why navigation, save, and quit commands change Editor State without modifying the Document, and why state transitions matter more than text edits.
---

Not every command changes the contents of the Document.

This distinction is important because it is easy to associate the Command Engine primarily with text editing. In reality, the Command Engine executes all editor commands, including commands that affect navigation, application state, or the relationship between the in-memory Document and the file system.

Consider three commands:

```text
MOVE_CURSOR_LEFT
SAVE_DOCUMENT
QUIT_EDITOR
```

None of these directly changes the Document's contents.

Yet each produces a meaningful state transition:

```text
MOVE_CURSOR_LEFT
        │
        ▼
     Cursor
```

```text
SAVE_DOCUMENT
   │
   ▼
File System / Dirty Flag
```

```text
QUIT_EDITOR
   │
   ▼
Application State
```

The Document is therefore only one part of the state affected by command execution.

## Navigation Commands

Navigation commands change the user's position within the Document without changing its contents.

For example:

```text
MOVE_CURSOR_LEFT
MOVE_CURSOR_RIGHT
MOVE_CURSOR_UP
MOVE_CURSOR_DOWN
```

Their primary effect is on the Cursor:

```text
MOVE_CURSOR_LEFT
       │
       ▼
Cursor Position
       │
       ▼
Editor State
```

The text remains exactly the same.

For example, if the Document contains:

```text
Hello
World
```

moving the cursor does not change either line:

```text
Document
────────────
Hello
World
```

Only the logical cursor position changes.

This means navigation commands should not mark the Document as modified.

The movement itself is still governed by the Cursor Engine's rules. The Command Engine simply coordinates the requested movement.

## Save

`SAVE_DOCUMENT` is another command that does not modify the Document.

Instead, it synchronizes the current in-memory Document with its persistent representation:

```text
Editor State
    │
    │ Document
    ▼
File Manager
    │
    ▼
File on Disk
```

The contents of the Document remain unchanged.

What changes is the relationship between the in-memory state and the file on disk.

Before saving:

```text
Document
    │
    ├── current contents
    │
    └── Dirty = true
```

After a successful save:

```text
Document
    │
    ├── same contents
    │
    └── Dirty = false
```

This is an important distinction:

> **Saving a document does not edit the document. It persists the document.**

The Command Engine coordinates this operation, while the File Manager performs the file-system interaction.

If the save fails, the Document should remain unchanged and the editor should report the failure through its normal error-handling path.

## Quit

`QUIT_EDITOR` does not modify the Document either.

Instead, it changes the application's running state:

```text
QUIT_EDITOR
  │
  ▼
Running = false
  │
  ▼
Exit & Cleanup
```

The command therefore affects the lifecycle of the application rather than the contents of the Document.

The actual cleanup work remains the responsibility of the appropriate platform components. In particular, terminal settings must be restored before the application terminates.

This keeps the `QUIT_EDITOR` command conceptually simple:

> The command requests termination; the components responsible for application and terminal state perform the necessary cleanup.

## Different Commands, Different State Effects

The examples above demonstrate why command categories should not be defined solely by whether a command modifies the Document.

A more useful view is to consider **which part of the Editor State a command affects**:

| Command             | Document | Cursor | Dirty Flag | File System | Application |
| ------------------- | -------: | -----: | ----------: | ----------: | ----------: |
| `MOVE_CURSOR_LEFT`  |        — |      ✓ |           — |           — |           — |
| `MOVE_CURSOR_RIGHT` |        — |      ✓ |           — |           — |           — |
| `MOVE_CURSOR_UP`    |        — |      ✓ |           — |           — |           — |
| `MOVE_CURSOR_DOWN`  |        — |      ✓ |           — |           — |           — |
| `INSERT_CHARACTER`  |        ✓ |      ✓ |           ✓ |           — |           — |
| `DELETE_PREVIOUS_CHARACTER` | ✓ |      ✓ |           ✓ |           — |           — |
| `DELETE_CHARACTER`  |        ✓ |      ✓ |           ✓ |           — |           — |
| `SPLIT_LINE`        |        ✓ |      ✓ |           ✓ |           — |           — |
| `SAVE_DOCUMENT`     |        — |      — |           ✓ |           ✓ |           — |
| `QUIT_EDITOR`       |        — |      — |           — |           — |           ✓ |

The table is not intended to define new ownership rules. It simply shows the different effects that commands can have.

A command can therefore be meaningful even when the Document itself remains unchanged.

## State Change Versus Document Change

This leads to an important distinction:

```text
Document Change
        ≠
Editor State Change
```

Editing commands generally cause both:

```text
INSERT_CHARACTER
       │
       ├── Document changes
       ├── Cursor changes
       └── Dirty Flag changes
```

Navigation commands cause an Editor State change without a Document change:

```text
MOVE_CURSOR_LEFT
       │
       └── Cursor changes
```

A successful save changes the persistence state without changing the Document:

```text
SAVE_DOCUMENT
 │
 ├── Document remains unchanged
 └── Dirty Flag changes
```

Quit changes application state:

```text
QUIT_EDITOR
 │
 └── Running state changes
```

This distinction is useful because the Command Engine should reason about **state transitions**, not merely text modifications.

## Why This Matters for the Command Engine

If the Command Engine treated every command as a Document operation, it would create unnecessary coupling between unrelated parts of the system.

For example, a cursor movement should not need to interact with the Document simply because it is being executed through the same Command Engine.

Likewise, `SAVE_DOCUMENT` should not modify the Document merely because it is classified as a command.

Instead, each command should affect only the state required by its operation:

```text
Command
   │
   ▼
Required State
   │
   ▼
State Transition
```

This keeps commands focused and makes their effects easier to reason about.

## The Command Engine's Broader Role

The Command Engine is therefore better understood as the editor's **state-transition coordinator** rather than its text-editing component.

Its command set includes operations that:

- navigate through the Document,
- modify the Document,
- persist the Document,
- communicate application state changes, and
- eventually support other editor behaviors.

The common characteristic is not that these commands modify text.

The common characteristic is that they represent **intentional operations on the editor**.

```text
                  Commands
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
   Navigation     Editing      Application
        │            │            │
        ▼            ▼            ▼
     Cursor      Document      Lifecycle
                     │
                     ▼
                Editor State
```

This broader view keeps the Command Engine aligned with its architectural purpose: **executing editor commands and coordinating their resulting state changes, whether or not the Document itself is modified.**

## Summary

Not every command changes the contents of the Document. Navigation commands move the Cursor, `SAVE_DOCUMENT` persists the Document without editing it, and `QUIT_EDITOR` changes the application's running state. Each still produces a meaningful state transition.

The distinction between a Document change and an Editor State change is central: the Command Engine is a **state-transition coordinator**, not a text-editing component.
