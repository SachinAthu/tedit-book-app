## Introduction

By this point, the editor has a well-defined internal architecture. Input is translated into commands, commands update the editor state, and the document and cursor maintain the logical state of the editing session. However, none of that state is directly visible to the user.

The terminal only displays the result of the editor's rendering process.

Rendering is therefore the boundary between the editor's internal world and the user's visible world. The renderer reads the current editor state and transforms it into a visual representation containing the document, status bar, message bar, and cursor. It then produces the terminal output necessary to make that representation visible. The renderer does not decide what the document contains or how editing operations work; its responsibility is to represent the state that already exists.

This chapter focuses on the theory behind that process. Before implementing the renderer, we need to understand the different ways interactive software can construct and display visual output. We will examine immediate-mode and retained-mode rendering, the concept of a frame, the relationship between rendering and interactive event loops, and the purpose of double buffering.

These concepts also reveal an important distinction between graphical applications and terminal applications. A terminal editor does not draw pixels directly. Instead, it constructs terminal output that causes the terminal emulator to display the desired result. Understanding this boundary helps explain why our editor can use a relatively simple rendering strategy while still benefiting from an intermediate representation of the screen.

The goal is not to build a sophisticated graphical rendering system. Our editor deliberately favors simplicity, predictability, and educational value. The purpose of this chapter is to establish the reasoning behind that approach so that the Screen Buffer introduced in the next chapter is a natural consequence of the architecture rather than an unexplained implementation detail.

## Learning Objectives

By the end of the chapter, readers should understand:

- What a rendering model is
- The difference between immediate-mode and retained-mode rendering
- What a frame represents
- How game loops relate to interactive rendering
- What double buffering solves
- How terminal rendering differs from graphical rendering
- Why the editor uses an application-side frame representation
- How these decisions lead naturally into the Screen Buffer of Chapter 18

This keeps the chapter conceptual rather than implementation-heavy.
