Rendering is the boundary between the editor's internal world and the user's visible world. It answers a single question: **given the current Editor State, how should the editor construct the visual frame that represents that state on the terminal?**

The chapter established the foundation for answering that question. The **Editor State** — the Document, Cursor, Viewport, and related state — records what is true about the editing session, but it is not itself a representation of what the user sees. The **frame** is that representation: a complete, point-in-time snapshot of the visible interface, derived from the current state rather than a second source of truth. The renderer is therefore a read-only consumer of state.

The chapter then compared the two fundamental rendering models. **Immediate-mode rendering** derives the visual output from the current state each time a frame is produced and keeps no persistent interface representation. **Retained-mode rendering** maintains a persistent visual model and updates it incrementally. Immediate mode is simpler to reason about; retained mode trades that simplicity for reduced repeated work. Our editor favors immediate mode, which aligns with its full-redraw strategy — though the two ideas remain distinct.

Rendering happens inside an **event-driven loop**, not a continuously running game loop. Each event produces a state change, and each state change produces one frame. Rendering is therefore a consequence of state changes, never a participant in them.

**Double buffering** separates frame construction from presentation so the terminal never observes a partially built frame. In a terminal this is applied at the application level rather than through graphical framebuffers: the editor builds the frame in memory, then emits the terminal output that describes it. This is not retained-mode rendering; the Editor State remains the source of truth, and the buffer is only a boundary between constructing and presenting.

Finally, the chapter confirmed the chosen design: an **application-side frame representation** — the Screen Buffer — that sits between frame construction and terminal output. The complete pipeline is therefore a transformation:

```text
Editor State
     │
     ▼
Rendering Model
     │
     ▼
Frame
     │
     ▼
Screen Representation
     │
     ▼
Terminal
```

The central idea is that **rendering is a transformation from logical state into visual state**.

The central design choices — immediate-mode rendering, event-driven (one event, one frame) rendering, and the application-side frame representation — are recorded as **ADR-017: Rendering Model and Frame Representation**.

2. Why is the renderer a read-only consumer of state rather than an owner of it?
3. What is the difference between immediate-mode and retained-mode rendering?
4. Why does the editor render once per event rather than continuously?
5. What problem does double buffering solve?
6. Why is double buffering not the same as retained-mode rendering?
7. Why does a terminal editor work in character cells rather than pixels?

### Thought Experiments

1. If the editor rendered continuously like a game loop, what work would be wasted when the user does nothing?
2. Suppose the editor adopted a retained visual model. What new synchronization problems would appear between that model and the Editor State?
3. What would go wrong if the renderer wrote directly to the terminal while still deciding what the frame should contain?

## Common Mistakes

### Confusing application state with visual state

The Document and Cursor record what is true; the frame records what should be visible. Treating them as the same representation obscures the renderer's role as a pure transformation.

### Assuming terminals render pixels like graphical applications

A terminal editor communicates through characters and control sequences. The terminal emulator interprets that output and produces the display; the editor never draws pixels directly.

### Assuming double buffering requires GPU framebuffers

Double buffering is a separation of constructing from presenting, not a hardware requirement. In a terminal editor the same principle is applied with an application-side in-memory frame.

### Treating immediate mode and full redraw as exactly synonymous

Immediate mode describes how the visual result is derived; full redraw describes how much of the display is regenerated. The editor can construct a complete frame while still using an intermediate buffer before sending output.

### Assuming retained mode is automatically faster

Retained mode avoids reconstructing unchanged elements, but it introduces synchronization and state-management costs. For a small terminal editor, immediate mode is often the better trade.

### Optimizing rendering before measuring the actual bottleneck

A terminal frame is at most a few thousand character cells. Optimizing for a hypothetical large or high-frequency workload contradicts the editor's actual requirements.

### Mixing terminal output with state mutation

Writing to the terminal during frame construction couples the renderer to the output stream and risks exposing partial frames. Rendering should derive a complete frame from a consistent state, then present it.
