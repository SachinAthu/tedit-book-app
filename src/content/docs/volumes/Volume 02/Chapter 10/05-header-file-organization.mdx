Header files define the public interfaces between modules. They allow one module to use the functionality provided by another without exposing its internal implementation. Because every module depends on header files, organizing them correctly is essential for building a maintainable C project.

A poorly designed header can introduce unnecessary dependencies, increase compilation time, expose implementation details, and even prevent the project from compiling. A well-designed header, on the other hand, acts as a clean and stable contract between modules.

In this section, we will examine the principles that every header file in our editor should follow.

## One Header Per Module

Throughout this book, each module exposes exactly one primary public header.

For example:

```text
renderer/
├── renderer.h
└── renderer.c

document/
├── document.h
└── document.c

cursor/
├── cursor.h
└── cursor.c
```

The header defines everything another module needs in order to use that module.

If another part of the editor needs rendering services, it includes:

```c
#include "renderer.h"
```

If it needs document operations, it includes:

```c
#include "document.h"
```

This consistency makes the project easy to navigate because every module follows the same convention.

## Include Guards

A header file may be included by multiple source files.

For example:

```text
main.c
    │
    ├─────────────┐
    ▼             ▼
input.h      renderer.h
    │             │
    └──────┬──────┘
           ▼
      common.h
```

Without protection, the compiler could process the contents of `common.h` multiple times, leading to duplicate declarations and compilation errors.

To prevent this, every header file should use an **include guard**.

```c
#ifndef RENDERER_H
#define RENDERER_H

/* declarations */

#endif
```

The first time the header is included, the compiler defines the macro `RENDERER_H` and processes the file normally.

If the header is encountered again later, the compiler sees that `RENDERER_H` has already been defined and skips the remainder of the file.

Include guards ensure that each header is processed only once during compilation, regardless of how many times it is included.

## What Belongs in a Header?

A header file should contain only declarations that form the module's public interface.

Typical contents include:

- Function declarations
- Public structures
- Public enumerations
- Public type aliases
- Public constants
- Function pointer types (when needed)

For example:

```c
#ifndef CURSOR_H
#define CURSOR_H

typedef struct Cursor Cursor;

void cursor_move_left(Cursor *cursor);
void cursor_move_right(Cursor *cursor);

#endif
```

Everything in this file is part of the Cursor module's public API.

Any module that includes `cursor.h` immediately knows what services the Cursor module provides.

## What Should Stay Out of a Header?

A common mistake is placing implementation details inside header files.

Headers should **not** contain:

- Function implementations
- Internal helper functions
- Private variables
- Temporary implementation details
- Unnecessary `#include` directives

For example, this is poor design:

```c
void move_cursor_internal(void);
void validate_position(void);
void calculate_screen_offset(void);
```

These functions are implementation details.

Other modules should not know they exist.

Instead, they belong inside the module's source file.

Keeping implementation details private reduces coupling and allows the module to evolve without affecting other parts of the project.

## Minimize Dependencies

One of the goals of header organization is to minimize dependencies between modules.

Every time a header includes another header, it creates an additional dependency.

For example:

```text
renderer.h
      │
      ▼
document.h
      │
      ▼
cursor.h
      │
      ▼
terminal.h
```

As these dependency chains grow, compilation becomes slower and modules become more tightly coupled.

A good header includes only the declarations it genuinely requires.

Reducing unnecessary dependencies makes the project easier to maintain and simplifies future refactoring.

## Forward Declarations

Sometimes a header needs to refer to a type without knowing its complete definition.

In these situations, a **forward declaration** can be used instead of including another header.

For example, suppose the Renderer needs a pointer to an `EditorState`.

Rather than including `state.h`, the header can simply declare that the type exists.

```c
typedef struct EditorState EditorState;

void renderer_draw(EditorState *editor);
```

The compiler now knows that `EditorState` is a structure type, even though it has not yet seen its full definition.

The complete definition can remain inside the appropriate source file.

Forward declarations reduce dependencies and help prevent circular includes between modules.

We will use this technique throughout the implementation chapters.

## Keep Headers Stable

Header files represent the public contracts of a module.

Changing a header affects every source file that includes it.

For this reason, public interfaces should remain as stable as possible.

If the implementation of a module changes but its public behavior remains the same, the header often requires no modification at all.

For example, the Renderer may switch from one rendering algorithm to another.

As long as the public function remains:

```c
void renderer_draw(EditorState *editor);
```

the rest of the project continues to work without modification.

Stable interfaces reduce the impact of internal changes and make the system easier to evolve.

<Aside type="tip" title="Engineering Insights" icon="rocket">

Think of a header file as the front door to a module. Visitors should be able to see **what services are available**, but they should not be able to walk through the house and inspect every room.

A module with a small, carefully designed header is easier to understand, easier to test, and easier to modify than one that exposes every detail of its implementation. Professional software often places as much effort into designing clean interfaces as it does into writing the implementation behind them.

</Aside>

## Summary

Header files define the public interfaces between modules. A well-organized header exposes only the declarations that other modules need, protects itself with include guards, minimizes unnecessary dependencies, and hides implementation details behind a stable interface. By treating headers as contracts rather than implementation files, we reinforce the modular architecture established throughout the previous chapters.

In the next section, we will examine **module interfaces** in greater detail and explore how modules communicate through well-defined APIs while remaining independent of each other's internal implementations.
