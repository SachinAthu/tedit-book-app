In the previous section, we introduced the **Event Loop** as the central mechanism that drives the editor. The loop repeatedly waits for an event, processes it, updates the **Editor State**, and renders a new frame.

A natural question now arises:

> **What kinds of events does the editor actually receive?**

Many people initially think that events consist only of keyboard input. While keyboard events are certainly the most common, they represent only one category of events that an interactive application must handle.

Our editor processes several different kinds of events, each originating from a different source and serving a different purpose.

Understanding these event categories helps explain why an event-driven architecture is both flexible and extensible.

## Keyboard Events

The majority of events originate directly from the user.

Whenever a key is pressed, the terminal delivers the corresponding input to the editor. The **Input Handler** reads the raw bytes, the **Input Parser** interprets them into a structured event, the **Input Engine** maps that event to a command, and the resulting command is passed to the **Command Engine**.

Examples include:

```text
'A'
Backspace
Enter
Arrow Left
Arrow Right
Arrow Up
Arrow Down
Ctrl+S
Ctrl+Q
```

Although these appear very different from the user's perspective, the editor treats them uniformly.

Each key press becomes a discrete event processed by the **Event Loop**.

For example:

```text
Keyboard

↓

Input Handler

↓

Input Parser

↓

KEY_ARROW_LEFT

↓

Input Engine

↓

MOVE_CURSOR_LEFT

↓

Command Engine
```

The **Command Engine** does not care how the key was encoded by the terminal. The **Input Engine** maps the structured event to a command, and the Command Engine simply executes that command.

## System Events

Not every event originates from the keyboard.

Some events are generated by the operating system or the terminal environment.

Examples include:

- Window resize
- Startup
- Shutdown

Unlike keyboard events, these are not initiated by editing actions. Instead, they notify the application that something in its environment has changed.

Consider a terminal resize.

```text
Terminal Window

↓

Size Changes

↓

Resize Event

↓

Update Screen Size

↓

Adjust Viewport

↓

Render Frame
```

The user did not explicitly request the editor to redraw the screen, yet the display must still be updated to reflect the new terminal dimensions.

Similarly, startup and shutdown can also be viewed as system events that trigger specific initialization and cleanup procedures.

Thinking of these operations as events reinforces the idea that the **Event Loop** responds to changes in both user input and the surrounding environment.

## Internal Events

Some events originate entirely within the editor itself.

These are often the result of another event being processed.

Examples include:

- Cursor moved
- Document modified
- File loaded
- Status message updated

For example, inserting a character produces more than a single action.

```text
Key Press

↓

Insert Character

↓

Document Modified

↓

Cursor Moved

↓

Render Frame
```

The original keyboard event causes several changes inside the editor.

Rather than treating these changes as unrelated operations, we can view them as internal events that update different parts of the **Editor State**.

Similarly, after a successful save operation:

```text
Ctrl+S

↓

File Saved

↓

Dirty Flag Cleared

↓

Status Message Updated

↓

Render Frame
```

These internal events ensure that all parts of the editor remain synchronized without requiring unrelated components to communicate directly.

## Events Trigger Other Events

One important observation is that events often lead to additional events.

A single user action may trigger an entire sequence of internal activities.

For example:

```text
Ctrl+S
    │
    ▼
Save File
    │
    ▼
File Written
    │
    ▼
Dirty Flag Cleared
    │
    ▼
Status Message Updated
    │
    ▼
Render Frame
```

From the user's perspective, saving a file appears to be one operation.

Internally, however, it consists of several coordinated steps that update different parts of the application.

This layered processing allows each component to focus on its own responsibility while keeping the overall system organized.

## A Unified View of Events

Although events originate from different sources, the editor processes them using the same architectural pipeline.

```text
                 Event
                   │
      ┌────────────┼────────────┐
      │            │            │
      ▼            ▼            ▼
Keyboard       System       Internal
      │            │            │
      └────────────┼────────────┘
                   │
                   ▼
            Event Loop
                   │
                   ▼
          Update Editor State
                   │
                   ▼
             Render Frame
```

This unified approach is one of the strengths of event-driven software.

Whether the event is a key press, a terminal resize, or an internal state change, the editor handles it within the same execution model.

The components responsible for processing the event may differ, but the overall architecture remains consistent.

## Why This Matters

Recognizing that not all events originate from the user prepares us for the more sophisticated behavior of professional software systems.

As additional features are introduced in later volumes—such as search, syntax highlighting, configuration changes, or plugin support—they can often be expressed as new kinds of events rather than requiring changes to the overall architecture.

This is one of the reasons event-driven architectures scale so well.

New behavior is introduced by defining new events and corresponding handlers, while the **Event Loop** itself remains unchanged.

<Aside type="tip" title="Engineering Insights" icon="rocket">

A common misconception is that an event-driven application responds only to user input. In reality, any significant change in the application's environment or internal state can be represented as an event. By treating keyboard actions, system notifications, and internal state changes within a single processing model, the editor maintains a simple and extensible architecture that accommodates new functionality without altering its fundamental execution flow.

</Aside>

## Summary

In this section, we examined the three categories of events processed by the editor: **keyboard events** from user input, **system events** from the operating environment (such as terminal resizes), and **internal events** generated by the editor itself (such as cursor movement or document modification). We saw that events often trigger other events—a single key press can cascade through multiple internal state changes—and that the editor handles all event types through a unified architecture regardless of their source.

Now that we understand what kinds of events the editor receives, the natural next question is: what happens inside the **"Process the Event"** step of the Event Loop?
