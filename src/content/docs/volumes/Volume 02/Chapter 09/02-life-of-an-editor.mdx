---
title: 9.2 The Life of an Editor
description: The editor's lifecycle from startup through the main loop to shutdown.
---

When we think about a text editor, it is easy to focus on individual features such as inserting characters, moving the cursor, or saving a file. In reality, however, these are only small parts of a much larger execution process. From the moment the editor starts until it exits, it follows a well-defined lifecycle that determines how it initializes, responds to user input, updates its state, and eventually shuts down.

Understanding this lifecycle provides a high-level view of the editor's runtime behavior. Rather than thinking of the editor as a collection of independent features, we can see it as a continuously running system whose components cooperate to provide an interactive editing experience.

At a high level, the lifecycle of our editor can be represented as follows:

```text
+----------------------+
|   Start Program      |
+----------------------+
           │
           ▼
+----------------------+
|    Initialize        |
+----------------------+
           │
           ▼
+----------------------+
|  Enter Event Loop    |
+----------------------+
           │
           ▼
+----------------------+
|  Wait for an Event   |
+----------------------+
           │
           ▼
+----------------------+
|  Process the Event   |
+----------------------+
           │
           ▼
+----------------------+
|   Update State       |
+----------------------+
           │
           ▼
+----------------------+
|  Render New Frame    |
+----------------------+
           │
           ▼
      More Events?
           │
      Yes ─┘
           │
          No
           ▼
+----------------------+
| Exit & Cleanup       |
+----------------------+
```

Although the diagram appears simple, it captures the entire lifetime of the application. Every feature discussed throughout the rest of the book fits somewhere within this sequence.

## Step 1 — Start the Program

The lifecycle begins when the operating system launches the editor. This may occur when the user executes the program from the terminal, optionally providing the name of a file to open.

At this point, the operating system creates a new process, allocates memory for the program, and transfers execution to the editor's entry point (`main()`).

The editor itself has not yet begun editing a document—it has only just started executing.

## Step 2 — Initialize the Editor

Before the editor can respond to user input, it must prepare its runtime environment.

Typical initialization tasks include:

- Creating the initial **Editor State**.
- Enabling raw terminal mode.
- Determining the terminal dimensions.
- Loading a document if one was specified.
- Preparing the renderer.
- Drawing the initial screen.

These operations occur only once, immediately after startup.

At the end of this phase, the editor has everything it needs to begin interacting with the user.

## Step 3 — Enter the Event Loop

Once initialization is complete, the editor enters its **Event Loop**.

This marks the beginning of the application's normal operation. From this point forward, the editor repeatedly waits for events, processes them, updates its internal state, and redraws the screen.

Unlike a utility program that performs one task and exits, a text editor spends nearly all of its lifetime inside this loop.

## Step 4 — Wait for an Event

Most of the time, nothing is happening.

The editor simply waits for the next event to occur. This event may be generated by:

- the user pressing a key,
- the terminal being resized,
- or another part of the system requiring attention.

Waiting for events allows the editor to remain responsive without performing unnecessary work.

## Step 5 — Process the Event

When an event arrives, the editor determines what it means and what action should be taken.

For example:

- a printable character inserts text,
- an arrow key moves the cursor,
- **Ctrl+S** saves the document,
- **Ctrl+Q** exits the application.

At this stage, the event is translated into a meaningful editing operation.

## Step 6 — Update the Editor State

Most events require changes to the **Editor State**, which acts as the application's single source of truth. As established in the previous chapter, components cooperate by reading from and updating this shared state rather than maintaining their own independent copies.

Depending on the event, the editor might:

- insert or delete text,
- move the cursor,
- update the viewport,
- change the current filename,
- mark the document as modified,
- or display a status message.

The editor's state now reflects the result of the user's action.

## Step 7 — Render a New Frame

After the state has been updated, the renderer generates a new visual representation of the editor.

Rather than drawing only the parts that changed, our editor follows a **full-screen redraw** strategy. It reads the current Editor State and redraws the entire visible interface, ensuring that the display always reflects the latest application state. This architectural decision was introduced in the previous chapter and simplifies the rendering process by making each frame a complete representation of the current state.

Once rendering is complete, the editor returns to waiting for the next event.

## Step 8 — Exit and Cleanup

Eventually, the user chooses to exit the editor.

Before terminating, the application performs its cleanup operations, such as restoring the terminal to its original configuration and releasing any resources it acquired during execution. Restoring the terminal is particularly important because the editor temporarily enables raw mode while it is running.

After cleanup is complete, the process terminates and control returns to the operating system.

## Summary

In this section, we introduced the lifecycle of the editor. We saw that, although the editor performs many different operations, they all follow the same pattern: initialization prepares the application, the Event Loop repeatedly processes events and updates the Editor State, and cleanup restores the environment before the program exits.

In the next section, we will examine the **Initialization Phase** in detail—everything that happens before the editor enters the Event Loop.
