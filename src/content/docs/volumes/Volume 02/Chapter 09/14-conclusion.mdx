This chapter introduced the **event-driven architecture** that governs how our editor operates at runtime. While Chapter 8 defined the static structure of the system—its components, responsibilities, and dependencies—this chapter explained how those components cooperate moment by moment as the application runs.

We began by defining what an event-driven system is: an application whose behavior is determined by events rather than a fixed sequence of operations. We saw why this model is a natural fit for a text editor, which has nothing to do until the user presses a key or the environment changes. We then walked through the complete lifecycle of the editor, from startup through the initialization phase (parsing arguments, enabling raw mode, loading the document, and rendering the first frame) to the **Event Loop**—the central mechanism that reads input, processes events, updates state, renders each frame, and repeats until exit.

We examined the different types of events the editor handles (keyboard, system, and internal), traced how a single key press flows through the entire pipeline from the terminal through the Input Parser, Input Engine, Command Engine, Editor State, and Renderer, and clarified the important distinction between raw events and semantic commands. We saw that the Editor State acts as the single source of truth and that the Renderer is a pure, read-only transformation from state to screen. We explored why a **full-screen redraw** strategy, sequential single-threaded execution, and lightweight command processing together keep the editor responsive without requiring concurrency or incremental rendering. Finally, we discussed how runtime errors are handled within the loop without crashing the editor or leaving it in an inconsistent state.

With both the static architecture and the runtime behavior now thoroughly understood, we are ready to begin translating this design into working code.
