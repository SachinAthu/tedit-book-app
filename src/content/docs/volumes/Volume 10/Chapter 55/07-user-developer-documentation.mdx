## Implementation goal

A release is not complete merely because the source compiles and the tests pass. Users need to know how to obtain, verify, install, launch, and remove the editor. Developers need to know how to build it, run its tests, understand its architecture, and make changes without violating established design decisions.

Documentation must describe the software that actually exists. It must not advertise packages that have not been published, claim support for operating systems that have not been tested, or promise features that remain unimplemented.

This section establishes two documentation paths:

- User path: Obtain the editor, verify the download, install or build it, use it, and troubleshoot common problems.
- Developer path: Obtain the source, configure and build the project, run tests, understand module boundaries, and contribute changes.

## Finding and downloading a release

A user should begin at the project's official release page. For a GitHub-hosted project, that is normally the repository's Releases page.

The release page should identify:

- The version number and release date.
- Supported operating systems and architectures.
- Available downloads and their intended use.
- Installation or build instructions.
- Checksum files and verification instructions.
- Known limitations and relevant changes.

For the current project, the Chapter 55 source archive is a release candidate, not evidence that a public GitHub release already exists. A public release URL should be documented only after the project has actually published one.

A user should select the artifact appropriate to their needs. A source archive requires a compiler and build tools; a precompiled executable has different compatibility requirements; and an operating-system package must match the user's distribution and architecture.

## Verify the downloaded file

Before extracting or installing an artifact, users should verify its checksum when a trusted checksum has been provided.

For example, if the downloaded files are:

```
tedit-v1.0.0.zip
tedit-v1.0.0.zip.sha256
```

run:

```bash
sha256sum -c tedit-v1.0.0.zip.sha256
```

Proceed only if verification succeeds. If it fails, download the artifact again from the official source and check the published checksum. Do not install a file that continues to fail verification.

Remember that a checksum confirms that the file matches the expected digest. If both the archive and checksum came from an untrusted or compromised source, the checksum alone cannot establish that the software is authentic.

## Build the editor from source

Building from source is the most direct installation path supported by the current project.

The user needs a compatible C compiler, CMake, and the dependencies required by the project. Python 3 is needed to run the POSIX pseudo-terminal integration test when that test is registered.

From the extracted repository root:

```bash
cmake -S . -B build/release \
    -DCMAKE_BUILD_TYPE=Release

cmake --build build/release

ctest --test-dir build/release --output-on-failure
```

If the build and tests succeed, the resulting executable is available at the path generated by the project's CMake configuration. The exact executable path should be confirmed from the repository's build configuration rather than assumed.

To run the editor, use that executable path and optionally supply a file path if the program supports opening a file from the command line.

For example, if the built executable is located at `build/release/tedit`:

```bash
./build/release/tedit
```

To open a file:

```bash
./build/release/tedit notes.txt
```

These commands assume the executable is named `tedit` and accepts a filename argument. The final user documentation must be checked against the actual executable name and command-line behavior before publication.

## Install on Debian and Ubuntu

When a tested Debian package is available, users can install it from a configured repository:

```bash
sudo apt install tedit
```

This requires a repository that provides the package. A GitHub Release alone does not make the package available through APT.

For a downloaded `.deb` package, the user can install the local file:

```bash
sudo apt install ./tedit_1.0.0_amd64.deb
```

The filename here is illustrative; users must use the actual downloaded filename.

If the project does not publish a Debian package, users should follow the documented source-build instructions instead. Do not instruct users to install a package that does not exist.

## Install on Fedora

If a compatible RPM package is published in a configured repository, users can install it with:

```bash
sudo dnf install tedit
```

For a downloaded RPM file:

```bash
sudo dnf install ./tedit-1.0.0-1.x86_64.rpm
```

The example filename is illustrative. The actual package name and architecture may differ.

A package should be installed only when it has been built and tested for the intended environment. If no RPM is available, the source-build instructions are the appropriate alternative.

## Install with Snap

If the project publishes a Snap package under the name `tedit`, a user with Snap support configured can install it using:

```bash
sudo snap install tedit
```

The user can remove it using:

```bash
sudo snap remove tedit
```

These commands describe the normal Snap workflow; they do not imply that this editor currently has a published Snap package. The final release documentation should link to the actual Snap listing only after publication.

## Run and remove the editor

User documentation should explain the basic lifecycle:

1. Launch the editor from a terminal.
2. Open a file, if supported by the command-line interface.
3. Edit and save the document using the documented keyboard commands.
4. Exit using the supported exit command.
5. Confirm that the terminal is restored to normal operation.

The documentation should also explain how to remove the program according to its installation method.

| Installation method           | Removal approach                                                         |
| ----------------------------- | ------------------------------------------------------------------------ |
| APT-managed package           | Remove through APT                                                       |
| DNF-managed package           | Remove through DNF                                                       |
| Snap package                  | Remove through Snap                                                      |
| Manually installed executable | Remove the installed executable and any project-created supporting files |
| Build directory only          | Remove the generated build directory when no longer needed               |

For example, a package installed through APT can normally be removed with:

```bash
sudo apt remove tedit
```

A package installed through DNF can normally be removed with:

```bash
sudo dnf remove tedit
```

Removal instructions should clarify whether user-created documents and configuration files are retained. The editor must never imply that uninstalling it will safely remove or manage a user's documents unless that behavior is deliberately implemented.

## Troubleshooting installation and execution

The user guide should include a short troubleshooting section.

| Symptom                           | Initial investigation                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------- |
| CMake cannot find a compiler      | Install a compatible C compiler and verify it is available on `PATH`.                   |
| CMake configuration fails         | Read the first configuration error and check the required build tools and dependencies. |
| Compilation fails                 | Review the compiler diagnostic and verify the documented source revision.               |
| Integration test is missing       | Check whether Python 3 and the required POSIX test facilities are available.            |
| Terminal display is incorrect     | Check terminal compatibility and the documented terminal requirements.                  |
| Checksum verification fails       | Re-download from the official source and verify against the published checksum.         |
| Package cannot be found           | Confirm the package is actually published in a repository configured on the system.     |
| Editor cannot open or save a file | Check the path, permissions, and error message; do not assume the operation succeeded.  |

Troubleshooting guidance should help users distinguish an application defect from a missing dependency, unsupported environment, or invalid installation assumption.

## Developer documentation

The developer guide should preserve the architecture and engineering workflow established throughout the book.

At minimum, it should document:

- Project structure: The responsibilities of the Core, Application, and Platform layers and the principal source directories.
- Build requirements: C99, CMake, the compiler, and any dependencies.
- Build configurations: Debug, Release, logging-enabled, and logging-disabled builds.
- Testing: CTest, unit tests, integration tests, and sanitizer configurations.
- Coding standards: Naming, ownership, error handling, and interface conventions.
- Architectural constraints: Dependency direction, state ownership, and the separation between rendering, command execution, and file persistence.
- Known limitations: Incomplete Unicode display-width support, non-ASCII filename display limitations, and remaining failure-injection gaps.
- Contribution workflow: Reviewing changes, running tests, recording architectural decisions, and preparing a release.

The documented build and test commands should be copied from verified project workflows, not independently invented in multiple documents. This reduces the chance that the README, developer guide, and CI configuration drift apart.

## Keep documentation synchronized with the implementation

Documentation can become incorrect even when the code remains correct. A command-line option may change, a package may be renamed, or a limitation may be fixed.

For that reason, documentation should be part of release review. Before publishing, verify that:

- All example commands match the actual build system.
- Keyboard shortcuts match the implemented input mappings.
- Download links point to real artifacts.
- Installation instructions match the package format.
- Platform claims match the platforms tested.
- Known issues reflect the current implementation.
- The license and reuse terms are explicit.

For this project, the source archive and documented source-build workflow are the immediate supported distribution path. Instructions for APT, DNF, and Snap should remain clearly conditional until the corresponding packages are built, tested, and published.

## Section conclusion

User and developer documentation completes the path from source code to a usable and maintainable application. A user should be able to identify the correct download, verify it, install or build the editor, run it, and remove it. A developer should be able to reproduce the build, run the tests, understand the architecture, and make changes without undermining established invariants.

The next section, 55.8 Final End-to-End Validation, will verify the release as a whole: not merely whether individual modules pass their tests, but whether a cleanly obtained build can be launched, used to edit and save a document, and exited without leaving the terminal in a broken state.
