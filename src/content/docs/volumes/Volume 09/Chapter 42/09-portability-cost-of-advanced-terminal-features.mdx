---
title: "42.9 The Portability Cost of Advanced Terminal Features"
description: "Weighs how advanced terminal features multiply protocols, capability combinations, and testing, raising portability and maintenance costs."
---

Advanced terminal capabilities do not only increase implementation complexity. They also increase the number of environments that an application must understand, test, and maintain.

Basic terminal interaction can already depend on terminal behavior and platform assumptions. Once an editor begins using optional features such as true color, mouse reporting, or terminal graphics, those assumptions become more significant.

The important issue is not simply whether a feature exists. The issue is:

> **How many different environments must the editor handle correctly when it depends on that feature?**

## A Fragmented Capability Landscape

For ordinary text rendering, the editor can target a relatively small set of fundamental terminal operations:

```text
Character Output
Cursor Movement
Screen Clearing
Terminal Size
Input Sequences
```

Advanced features introduce more variation:

```text
Advanced Feature
       │
       ├── Supported
       ├── Unsupported
       ├── Partially Supported
       └── Supported through another protocol
```

For example, an editor that wants to display graphical content might encounter one terminal with a supported graphics protocol, another with no graphics support, another with a different protocol, and another with partial or restricted support. The feature itself may be conceptually identical, but the implementation environment is not.

## Standard Features Versus Vendor-Specific Features

A major source of portability cost is the distinction between widely established terminal behavior and vendor-specific extensions:

```text
Terminal Capability
       │
       ├── Common terminal behavior
       │
       └── Vendor-specific extension
```

The more an editor depends on vendor-specific behavior, the more closely its platform layer becomes tied to particular terminal environments. Kitty graphics provide a clear example: an editor can conceptually support the Kitty graphics protocol, but that does not imply every terminal can render the same output. The protocol therefore becomes a platform-specific dependency.

More generally, the more optional capabilities an editor requires, the larger the environmental assumption becomes. This does not make such features undesirable; it means they should be explicitly classified as optional capabilities rather than silently becoming requirements.

## Protocol Selection

Supporting several terminal environments can lead to a protocol-selection problem:

```text
                 Graphics Requested
                         │
                         ▼
                 Detect Capabilities
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
           Protocol A  Protocol B  None
              │          │          │
              ▼          ▼          ▼
           Render      Render     Fallback
```

This is manageable when isolated inside the platform layer. It becomes problematic when protocol decisions spread through the rest of the application. A poor design might scatter `if Kitty / if Protocol B / if Protocol C / if unsupported` throughout rendering logic. A better design keeps those differences behind a stable interface:

```text
Renderer
   │
   ▼
Terminal Interface
   │
   ├── Protocol A
   ├── Protocol B
   └── Fallback
```

This follows the existing architectural rule that platform-specific behavior belongs at the platform boundary rather than inside the Core (ADR-030).

## Capability Matrices

As optional features increase, testing also becomes more complicated. Suppose the editor supports true color, mouse, and graphics, and each feature may be available or unavailable. Even without considering protocol differences, the theoretical combinations already form a matrix:

```text
Color   Mouse   Graphics
  no      no       no
  no      no       yes
  no      yes      no
  no      yes      yes
  yes     no       no
  yes     no       yes
  yes     yes      no
  yes     yes      yes
```

With multiple graphics protocols or different terminal behaviors, the matrix grows further. This does not mean every possible combination must necessarily receive identical testing effort. It demonstrates a more general problem:

> **Every optional capability increases the number of environmental states that the application may need to handle.**

## Portability Is More Than Compilation

An application may compile successfully on several systems and still have poor terminal portability. For a terminal editor, portability also includes building, starting, reading input correctly, rendering correctly, and handling terminal capabilities correctly:

```text
Builds
  +
Starts
  +
Reads input correctly
  +
Renders correctly
  +
Handles terminal capabilities correctly
```

Advanced terminal features increase the number of ways the last two conditions can fail. A terminal may lack a requested capability, interpret a protocol differently, expose only part of a feature, behave differently after resizing, or maintain graphical state differently from another terminal. Therefore, portability must be considered at the behavioral level, not only at the compilation level.

## The Cost of Supporting Multiple Protocols

Supporting multiple protocols may appear attractive, but it introduces additional code and testing requirements. The platform layer might eventually resemble:

```text
Terminal Interface
        │
        ├── Basic terminal output
        │
        ├── Graphics Backend A
        │
        ├── Graphics Backend B
        │
        └── Graphics Backend C
```

Each backend may require protocol-specific encoding, capability detection, lifecycle management, error handling, testing, and maintenance. The feature therefore has a cost beyond its visible implementation.

## Portability Versus Feature Richness

This produces a familiar engineering trade-off:

```text
More terminal features
        │
        ▼
More platform assumptions
        │
        ▼
More implementation and testing
        │
        ▼
Higher portability cost
```

Conversely:

```text
Fewer optional dependencies
        │
        ▼
Smaller platform boundary
        │
        ▼
Fewer environmental assumptions
        │
        ▼
Simpler portability
```

Neither direction is universally correct. A mature application may reasonably decide that a particular advanced feature is important enough to justify the additional complexity. The important point is that the cost should be recognized as an architectural decision rather than appearing accidentally through scattered feature additions.

## Why This Matters for Our Editor

Our editor is deliberately designed around a relatively small platform boundary. The project structure already separates the `terminal/` module from the Core modules such as `document/`, `cursor/`, `viewport/`, and `state/`. That structure gives us a natural place to contain advanced terminal differences:

```text
Core
 │
 │ platform-independent
 ▼
Renderer
 │
 ▼
Terminal Interface
 │
 ├── Basic terminal support
 ├── Optional color
 ├── Optional mouse
 └── Optional graphics
```

The Core does not need to know which terminal protocol is being used.

## Why the Baseline Should Remain Small

The SRS deliberately keeps the baseline editor focused on core terminal text editing and excludes advanced interaction such as mouse support from the initial scope. That makes the portability problem substantially smaller. The baseline environment can be understood as one stable platform boundary feeding core editor functionality, rather than many optional protocols producing many capability combinations, a large testing matrix, and greater maintenance cost. This is one reason advanced terminal capabilities should be introduced only when a concrete requirement justifies them.

## Capability Fragmentation Is an Architectural Concern

Terminal fragmentation should not be viewed merely as an inconvenience for users. It affects architecture. Every additional terminal capability can introduce:

```text
Capability
   ↓
Detection
   ↓
Protocol selection
   ↓
Implementation
   ↓
Fallback
   ↓
Testing
   ↓
Maintenance
```

If these concerns are isolated behind the platform boundary, the rest of the editor can remain stable. If they leak into the Core, the entire architecture becomes dependent on terminal-specific behavior. The existing dependency direction helps prevent this:

```text
Application
    │
    ▼
Core
    ▲
    │
Platform
```

The platform layer can adapt to terminal differences without forcing the Core to understand them.

## The Architectural Principle

Advanced terminal features therefore have two distinct costs:

```text
Feature Cost
├── Implementation complexity
└── Portability complexity
```

The second cost is easy to overlook. A feature that requires only a small amount of code may nevertheless require substantial capability detection, compatibility handling, and testing across different terminal environments.

The appropriate response is not to avoid advanced features altogether. Instead:

> **Keep terminal-specific differences behind the platform boundary, treat advanced capabilities as optional unless requirements make them mandatory, and avoid allowing portability concerns to leak into the editor's Core.**

This preserves the architecture while allowing future terminal-specific enhancements to be added when they provide sufficient value.

## Summary

Advanced terminal features increase implementation complexity and the number of environments an editor must understand, test, and maintain.

Vendor-specific protocols such as Kitty graphics create a fragmented capability landscape that grows the testing matrix and couples the platform layer to particular terminals unless differences are kept behind a stable interface.

The right response is to keep terminal-specific differences behind the platform boundary, treat advanced capabilities as optional unless requirements make them mandatory, and avoid letting portability concerns leak into the Core.

Keeping protocol selection and capability differences inside the Terminal Interface limits that cost, because the Core continues to depend only on stable editor concepts. A feature whose portability burden is not acknowledged tends to spread that burden through the rest of the architecture.
