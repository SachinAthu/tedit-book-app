By this point, we have seen that not every key on a keyboard produces a printable character. We have also learned that many special keys, such as the arrow keys, are transmitted as **ANSI escape sequences** rather than single bytes.

Arrow keys, however, are only a small part of the story.

Modern keyboards include many additional keys that applications rely on:

- Function keys (F1–F12, and sometimes beyond)
- Home
- End
- Insert
- Delete
- Page Up
- Page Down

A terminal editor must recognize these keys just as reliably as ordinary characters. Understanding how terminals encode them reveals why keyboard input is more complex than simply reading bytes from standard input.

## Why Function Keys Are Different

Unlike alphabetic keys, function keys have no corresponding ASCII character.

For example:

```
A
```

represents the printable character `'A'`.

But what printable character should **F5** represent?

There isn't one.

Instead of assigning new character values, terminals continue the same strategy used for the arrow keys: they transmit **escape sequences**.

Conceptually, pressing a function key looks like this:

```
F5

↓

Terminal Emulator

↓

ESC [ 1 5 ~

↓

Program
```

The application never receives a special "F5" byte. It receives a sequence of bytes that it must interpret as a single key event.

## Common Special Keys

Although the exact encoding varies between terminal emulators, many keys follow widely adopted conventions.

| Key       | Common Escape Sequence   |
| --------- | ------------------------ |
| Home      | `ESC [ H` or `ESC [ 1 ~` |
| End       | `ESC [ F` or `ESC [ 4 ~` |
| Insert    | `ESC [ 2 ~`              |
| Delete    | `ESC [ 3 ~`              |
| Page Up   | `ESC [ 5 ~`              |
| Page Down | `ESC [ 6 ~`              |

Notice that many of these sequences end with a tilde (`~`).

For example, pressing the **Delete** key may produce the following bytes:

```
Byte 1 : ESC
Byte 2 : [
Byte 3 : 3
Byte 4 : ~
```

Your program must recognize that these four bytes together represent a single Delete key press.

## Function Keys

Function keys are encoded in a similar way.

Depending on the terminal emulator, F1 through F12 may generate sequences such as:

| Key | Example Escape Sequence |
| --- | ----------------------- |
| F1  | `ESC O P`               |
| F2  | `ESC O Q`               |
| F3  | `ESC O R`               |
| F4  | `ESC O S`               |
| F5  | `ESC [ 15 ~`            |
| F6  | `ESC [ 17 ~`            |
| F7  | `ESC [ 18 ~`            |
| F8  | `ESC [ 19 ~`            |
| F9  | `ESC [ 20 ~`            |
| F10 | `ESC [ 21 ~`            |
| F11 | `ESC [ 23 ~`            |
| F12 | `ESC [ 24 ~`            |

These values should be viewed as representative examples rather than universal constants. Different terminals may use different sequences for the same key.

<Aside type="note" title="Note">

Terminal applications generally avoid depending on the exact byte sequence generated by every function key. Instead, they recognize the sequences used by the terminal emulators they intend to support or rely on terminal capability databases, such as **terminfo**, discussed later in this book.

</Aside>

## Why Do Different Sequences Exist?

You might wonder why there isn't a single standard for every key.

The answer lies in the history of computer terminals.

Long before graphical desktop environments existed, many manufacturers produced their own hardware terminals. Each model introduced its own keyboard layout and its own escape sequences.

For example:

```
Terminal A

F1

↓

ESC O P
```

```
Terminal B

F1

↓

ESC [ 11 ~
```

Both represent the same key, yet they use different byte sequences.

Modern terminal emulators often preserve these historical behaviors to remain compatible with older software. As a result, applications frequently encounter multiple valid encodings for the same key.

## Parsing a Longer Escape Sequence

Compared to an arrow key, some special keys produce longer sequences.

Consider the Delete key:

```
Delete

↓

ESC
[
3
~
```

From the program's perspective, the bytes arrive one after another:

```
read()

↓

27
91
51
126
```

Only after reading the entire sequence can the application conclude:

```
Delete Key
```

If it stopped after reading the first byte (`ESC`), it would incorrectly assume the user pressed the Escape key.

This illustrates why input handling often requires temporarily buffering incoming bytes until enough information has been received to identify the intended key.

## The Growing Complexity of Keyboard Input

At this point, several different categories of keyboard input exist:

```
Printable Character

↓

Single Byte
(or multiple bytes for UTF-8)
```

```
Control Shortcut

↓

Single ASCII Control Character
```

```
Arrow Key

↓

Escape Sequence
```

```
Function Key

↓

Longer Escape Sequence
```

An input parser cannot assume that each call to `read()` returns exactly one complete key press. Instead, it must determine whether the bytes represent:

- a printable character,
- a UTF-8 encoded character,
- a control character,
- a complete escape sequence, or
- the beginning of a longer sequence that has not yet fully arrived.

This increasing complexity is one of the main reasons why well-designed terminal applications separate **reading bytes** from **interpreting keys**.

<Aside type="tip" title="Engineering Insights" icon="rocket">

A common beginner's mistake is to assign arbitrary integer values directly to the raw escape sequences received from the terminal.

A more robust design is to translate every recognized sequence into an internal key representation.

For example:

```
Raw Bytes

ESC [ 3 ~

        ↓

Input Parser

        ↓

KEY_DELETE

        ↓

Editor Logic
```

The rest of the editor no longer needs to understand terminal-specific escape sequences. It simply reacts to abstract key events such as `KEY_DELETE`, `KEY_HOME`, or `KEY_F5`. This separation improves readability, simplifies testing, and makes it easier to support additional terminals in the future.

</Aside>

## Common Mistakes

- Assuming every key produces exactly one byte.
- Expecting all terminals to use identical escape sequences.
- Treating the Escape (`ESC`) key as equivalent to the start of every escape sequence.
- Processing incomplete escape sequences before all bytes have been received.
- Mixing terminal-specific byte parsing directly into editor logic instead of isolating it within the Input Parser.

## Summary

Function keys and other navigation keys extend the ideas introduced with arrow keys. Since these keys have no ASCII representation, terminal emulators encode them as escape sequences, often consisting of several bytes. Unfortunately, historical differences between terminal types mean that multiple valid encodings may exist for the same key.

For a terminal editor, this means that reading keyboard input is only the first step. The Input Parser must examine incoming bytes, recognize complete escape sequences, and translate them into internal key events that the rest of the editor can use without worrying about terminal-specific details.

In the next section, we will examine another layer of complexity: **modifier keys** such as **Shift**, **Ctrl**, **Alt**, and **Meta**, and how they alter the meaning of ordinary key presses.
